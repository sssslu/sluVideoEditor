### 1.9 객체 추적과 파일 보관

추적 UI는 원본 프레임의 영역 지정, 실제 프레임 시각에 따른 앞뒤 이동, 중간 기준점에서 양방향 분석, 잘못된 구간의 기준점 보완과 재분석을 지원합니다. 추정 위치·크기를 텍스트·이미지에 연결하며 수동 위치·키프레임을 유지합니다. 원본 분할과 조각별 편집, 삭제·실행 취소, 저장·재열기 및 실제 영상 출력의 연결을 검사했습니다. 추적은 윤곽 분리나 배경 제거가 아닙니다.

프로젝트 모아 저장은 원본 미디어와 추적 결과를 별도 자료 폴더에 복사하고 상대 경로와 내용 해시를 기록합니다. 누락된 추적 파일의 다시 연결은 저장 당시 추적 결과와 분석 당시 원본의 내용을 각각 확인합니다. 원본을 옮긴 뒤 추적 파일이 없는 상태로 다시 저장해도 원래 분석의 원본 확인 정보를 잃지 않습니다. 이름·머리글만 같은 변조 파일, 복사 중 원본 변경, 취소, 늦은 작업 완료를 검사합니다. 복구 수정 직후 관련 실제 소스 앱 5개 검사 묶음의 40개 항목이 통과했습니다. 120프레임 복구 출력의 4개 시각에서 독립적으로 계산한 추적 표식 중심과 차이는 2픽셀 미만입니다. 이 수치는 모델 정확도가 아닌 저장·복구·합성 결과의 일치 검사입니다.

모델 품질의 개발 표본은 OpenCV 공개 영상 3개의 총 2,428프레임이며 CPU와 DirectML 추적 상자 결과는 같았습니다. 정답 상자와 평균 겹침 비율은 영상별 0.7143 / 0.8556 / 0.5260입니다. 가림이 있는 세 번째 영상에서 성능이 낮으며 다른 촬영 조건의 정확도를 보장하지 않습니다. 모델 출력 점수를 정답 확률로 표시하지 않습니다. 연구 표본 영상은 배포물에서 제외합니다.

현재 버전의 실제 앱 IPC 검사에서는 같은 50프레임 구간을 CPU와 DirectML로 각각 분석해 원본 시각과 1픽셀 이내의 상자 일치를 확인했습니다. 실제 화면에서 만든 한글 자막의 100프레임 출력, 복구 후 120프레임 출력도 확인합니다. 일반 Chromium 인수의 별도 숨김 창에서는 UHD 영상의 600프레임을 분석하는 동안 실제 편집 입력 5회와 저장이 완료됐고, 취소 후 작업 프로세스와 부분 추적 파일이 남지 않았습니다. 이 검사는 입력·타이머 응답 검사이며 화면 재생 FPS나 일반적인 처리 속도 측정이 아닙니다. 검사 결과에는 실제 앱 버전·실행 경로·모델 및 소스 해시를 기록하고 EXE 검사에서는 실행 파일·ASAR 해시도 대조합니다.

개발 단계의 별도 UHD 부하 표본에서는 4K30 20초·600프레임을 1280픽셀 분석/DirectML로 처리할 때 제한된 디스크 역방향 버퍼가 반복 디코딩을 줄였습니다. 같은 기록을 만든 메모리 방식 65.24초, 디스크 방식 29.25–29.41초였습니다. CPU 디코딩·GPU 추론이며, 낮은 해상도 영상을 확대·반복한 부하 자료입니다. 원래 4K 촬영 영상의 추적 정확도나 실시간 재생 FPS·VRAM 상한을 뜻하지 않습니다. 근거는 `.test-artifacts/tracking-stress-stage-evidence.json`에 고정한 개발 단계 기록입니다.

새 프로젝트 형식은 8입니다. 이전 형식 1–7을 열 수 있지만 새로 저장한 프로젝트는 1.8 이하 앱에서 열 수 없습니다. 기존 파일을 열기만 하면 원본 프로젝트를 덮어쓰지 않습니다. 현재 사용법과 기능 제한은 `사용설명서.html`에 있습니다.

### 1.9 출력 성능 표본

이 PC에서 다른 앱 검사를 마친 뒤 일반 Chromium 인수로 측정했습니다. 50개 클립의 1080p30·66.562초 타임라인은 1,997프레임을 32.682초에 출력했습니다. 취소는 1.861초에 끝났으며 소유 작업 프로세스나 부분 출력이 남지 않았습니다. 여러 레이어·크롭·마스크 합성은 CPU, 인코딩은 NVENC입니다. 별도의 4K30·2초 표본은 빈 화면 1.304초, 자막 포함 1.716초였습니다.

CPU 프레임 버퍼 128MiB, GPU 프레임 버퍼 256MiB 설정이며 전체 앱 메모리나 VRAM 상한이 아닙니다. 합성 표본의 측정으로, 다른 PC·원본·편집의 속도를 보장하지 않습니다. 재현 명령은 `node scripts/benchmark-render.mjs`, `npx tsx scripts/benchmark-reverse-gpu.ts`, `node scripts/test-rich-captions.mjs --benchmark`입니다.

- 역재생은 17개 영상·오디오 구간에서 프레임 순서·표시 간격·마지막 프레임 길이와 디코딩한 전체 PCM 샘플을 비교했습니다. VFR, B 프레임, 양수 시작 시각, 10,002초 시각 오프셋, 지연·짧은 오디오, 다중 오디오 스트림을 포함합니다. 입력 파일은 유지하며 취소·원본 교체·실패 시 남은 작업 프로세스나 부분 결과를 검사했습니다.

- 실제 앱의 역재생 검사 24개는 버튼·프레임 이동·자르기 후 해제·실행 취소·복사·저장·다시 열기·보정 조합·작업 도중 편집과 잠금·프로젝트 전환을 포함합니다. 실제 CPU/NVENC 출력과 CUDA 분석·디코딩의 실행도 확인했습니다. 7종 원본과 결과의 네이티브 색상 비교는 평탄한 표본에서 채널당 2/255 이내였습니다. 검사 중 캡처 준비 시점 문제가 발견돼 준비 대기와 크기 지정을 보완했습니다. 당시 출력 파일의 별도 픽셀 검사는 기준과 0.466/255 이내로 일치했고, 수정한 화면 검사는 모두 통과했습니다.
- 90도 회전과 픽셀 비율 2:1·1:2 입력은 CPU 디코더 경로에서 표시 크기·방향과 오디오를 유지했습니다. 비교한 평탄한 색상 차이는 최대 2/255였습니다. HDR·고비트·투명 영상의 역재생은 지원하지 않습니다.
- 흔들림 보정은 임의의 컷 시작점에서 표시 중인 첫 프레임을 보존하고, 원본의 VFR 시각·색상 범위와 PCM 오디오를 유지하도록 수정했습니다. 8개 시각 구간과 6종 색상을 실제 앱에서 비교했습니다. 시작 시각이 양수인 MP4의 첫 탐색이 임시 재생 길이에 막히던 미리보기 문제도 수정했습니다.
- 새 저장 형식은 7입니다. 이전 형식 1–6을 열 수 있으며, 원본 프로젝트를 열기만 했을 때 덮어쓰지 않습니다. 새로 저장한 프로젝트는 1.7.1 이하 앱에서 열 수 없습니다.

자막의 실제 출력·미리보기 비교, 120fps 강조, 닫힌 로그 파이프의 EPIPE 처리와 한글·영어 Whisper 단어 인식 검사도 통과했습니다. 사용설명서의 링크·가로 넘침·버전 표기를 검사하고 실행·역재생 페이지를 화면에서 확인했습니다.

## 1.8 성능 표본

다른 자동 앱 검사가 끝난 뒤 이 PC에서 합성 24fps H.264 원본을 역재생했습니다. CPU 디코딩의 기본 프레임 버퍼는 128MiB, CUDA 분석·디코딩·역순 처리의 기본 프레임 버퍼는 256MiB이며 두 경로 모두 NVENC로 인코딩했습니다. 각 경로를 세 번 교차 실행한 중앙값입니다. GPU만 바꾸고 모든 조건을 고정한 비교는 아닙니다.

| 원본과 선택 구간 | 출력 프레임 | CPU 디코딩 + NVENC | CUDA 경로 + NVENC |
| --- | ---: | ---: | ---: |
| 1920×1080, 11.5초 | 277 | 4.083초 | 3.151초 |
| 3840×2160, 5.5초 | 133 | 10.632초 | 6.836초 |

모든 출력 프레임의 역순과 원본 불변을 검사했습니다. 재현 명령은 `npx tsx scripts/benchmark-reverse-gpu.ts`입니다. 메모리는 소유 프로세스를 약 50ms 간격과 조회 지연을 포함해 관측했습니다. 프레임 버퍼 설정은 전체 앱 메모리나 VRAM의 상한이 아니며, 디코더·인코더·드라이버 메모리가 추가됩니다.

별도의 50개 클립·66.562초 타임라인은 1,997프레임을 30.297초에 출력했습니다. 이 표본의 취소는 1.738초에 끝났으며 작업 프로세스와 부분 출력이 남지 않았습니다. 4K30·2초 자막 표본은 빈 화면 1.160초, 자막 포함 1.550초였습니다. 일반 Chromium 인수로 측정했고 자막 합성은 CPU, 인코딩은 NVENC입니다. 모두 합성 표본이며 실제 프로젝트나 다른 PC의 속도를 보장하지 않습니다.

## 1.7.1 색 범위와 파생 미디어

완전한 색상 태그를 가진 full-range H.264와 VP9, 태그가 일부 없는 SD·HD H.264, 제한 범위 H.264를 비교했습니다. 일부 입력에서 프록시와 출력이 원본 미리보기보다 밝거나 어두워지는 문제를 재현했습니다. 원본의 실제 네이티브 디코딩 규칙을 적용하고, 합성용 YUV와 프록시를 BT709 제한 범위로 통일했습니다. 직접 CUDA 출력은 원본 범위를 유지할 수 있는 조건에서 사용합니다.

- 실제 앱에서 6종 원본을 불투명도 1과 0.5로 CPU/NVENC 출력했습니다. 24개 파일, 총 576프레임을 확인했습니다. 평탄한 색상 표본은 실제 미리보기와 채널당 5/255 이내, 전체 영상의 평균 차이는 최대 1.662/255였습니다. 손실 압축과 색상 경계의 보간 때문에 전체 픽셀이 정확히 같은 것은 아닙니다.
- 별도 소프트웨어 출력 12건은 원본 Y/U/V 평면을 독립적인 BT601·BT709 수식으로 계산한 기준과 비교했습니다. YUVJ 형식 이름을 바꾸는 전처리에서 모든 평면의 바이트가 유지되는지도 확인했습니다.
- 원본의 색을 RGB로 변환한 뒤 PNG 썸네일에 sRGB 정보를 기록합니다. 기존의 비디오 감마 정보를 PNG에 복사해서 색이 어두워지는 문제를 수정했습니다. 썸네일과 원본 해상도 정지 프레임의 평탄한 색상 차이는 채널당 2/255 이내였습니다. 투명 영상의 알파 값도 별도로 검사했습니다.
- 1600×750 원본을 1280×600 프록시로 줄여도 네이티브 디코더가 색상 행렬을 바꾸지 않았습니다. 오래된 일반 프록시는 제외하고, 기존 JPEG·PNG 썸네일은 새로 생성합니다. 실제 프로젝트의 클립 편집과 미디어 이름을 유지하며, 실패했던 썸네일 생성도 다시 시도합니다.

근거: `tests/color-range.test.ts`, `scripts/e2e-color-range.mjs`. SDR 표본의 결과이며 HDR·광색역 또는 모든 코덱의 색 관리 검증을 의미하지 않습니다.

## 1.7.1 출력 성능 표본

다른 자동 UI 검사가 끝난 뒤 이 PC의 소스 엔진에서 측정했습니다. 재현 명령은 `node scripts/benchmark-render.mjs`이며 입력·소스 해시와 이전 측정 기록을 함께 보관합니다.

- 50개 클립의 66.562초·1080p30 타임라인: 1,997프레임을 30.780초에 출력했습니다. 측정한 자식 프로세스 작업 집합의 합은 최대 970.1MiB, Node 작업 집합은 최대 117.6MiB였습니다. 자식 프로세스 수와 오디오 디코더 수가 제한을 넘지 않았습니다. 취소 검사는 1.861초에 끝났고 남은 작업 프로세스나 게시된 부분 출력이 없었습니다. 여러 레이어·크롭·마스크 합성은 CPU, 인코딩은 NVENC입니다.
- 1080p30 원본 3초를 4K60·180프레임으로 확대: 직접 CUDA 경로는 첫 실행 1.974초, 반복 실행 1.731초·1.760초였습니다. CPU 디코딩·크기 조절 후 NVENC를 쓴 비교 경로는 1.935초·1.936초였습니다. 출력 해상도·프레임 수를 확인했고 디코딩한 오디오는 두 경로에서 바이트가 같았습니다. 네이티브 4K 원본의 디코딩 성능 측정은 아닙니다.
- 별도 4K30·2초 자막 표본: 빈 화면 1.279초, 자막 1.660초. 일반 Chromium 인수로 실행했으며 자막 합성은 CPU, 인코딩은 NVENC입니다.

합성 표본의 관측치로, 다른 PC나 실제 프로젝트의 속도를 보장하지 않습니다. 다른 앱의 부하와 캐시 상태를 통제하지 않았으므로 이전 버전 대비 개선율로 사용하지 않습니다.

## 1.7 원본 시계와 정지 프레임

- 시작 타임스탬프가 0이 아닌 MP4/MKV, MP3 인코더 지연, 프록시의 기준 시각을 구분했습니다. 기존 프로젝트는 원본 시간 정보를 갱신하되 클립 ID·트림·효과를 유지합니다. 소스 모니터 I/O와 실제 오디오 재생 시계도 검사했습니다.
- 소수 탐색·30/60/29.97fps·0.1배속·프레임 사이 클립 위치에서 실제 미리보기 61프레임이 원본 프레임 번호와 일치했습니다. 실제 IPC로 CPU/NVENC 파일 18개, 총 602프레임을 출력해 오류 0개였습니다. 완전한 BT709 정보를 가진 단일 클립에서는 CUDA 디코딩·크기 조절·NVENC 경로의 실행과 성공 종료도 확인했습니다.
- 원시 출력은 9개 속도·프레임률 조건의 324프레임과 소수 위치 3조건의 100프레임을 확인했습니다. 소수 위치에서 구간별 출력과 전체 출력의 바이트가 같습니다. 속도 곡선의 영상·음성 검사에서는 이상적인 연속 신호와 원본의 이산 프레임을 구분합니다. 분할 전후 각각 489프레임이 원본 시각 기준과 일치했으며, 이 표본의 음성 중심 시각 오차는 4ms 이내였습니다. 화면에 표시되는 프레임 구간의 중심을 기준으로 한 원시 영상·음성 차이는 최대 약 17.83ms였으므로 모든 조건에서 1/60초 이내라고 주장하지 않습니다.
- MP3 탐색 실패는 원본 패킷을 미리보기 전용 MP4로 옮겨 해결했습니다. 48kHz CBR 스테레오·44.1kHz VBR 모노·24kHz VBR 스테레오에서 원본 디코딩 PCM 구간의 바이트가 같았습니다. 뒤에 생길 수 있는 패딩은 원본 길이로 제한합니다. 동시 요청 재사용·원본 변경·취소·부분 파일 정리, MP3/M4A/Opus의 실제 레벨과 원본 PCM 비교도 통과했습니다.
- 정지 프레임은 원본에서 PNG를 만들고 현재 효과 상태를 고정해 선택 트랙에 삽입합니다. CFR/VFR·시작 시각 이동·회전·픽셀 종횡비·색상 태그·취소·원본 교체를 검사했습니다. 54개 원본 프레임 선택, 한 번의 실행 취소, 저장·다시 열기, 작업 도중 잠금·프로젝트 변경, 120fps 최소 길이를 확인했습니다.

불투명 정지 프레임 표본은 실제 원본 디코더와 PNG의 최대 채널 차이가 2/255 이내였고 평균은 0.028/255 미만이었습니다. 효과를 적용한 정지 구간의 평균 차이는 0.0038/255였습니다. 투명 VP9 표본의 알파는 전부 같았고 PNG 색은 독립적인 BT709 계산값과 일치했습니다. 다만 Chromium의 I420A 소프트웨어 변환과는 평균 0.59375/255, 최대 4/255 차이가 있었습니다. 원본 YUVA 값은 같았으며, 해당 경로의 근사 색상 계수는 [libyuv 구현](https://chromium.googlesource.com/libyuv/libyuv/+/HEAD/source/row_common.cc)에서 확인했습니다. HDR·광색역 정지 프레임과 모든 코덱의 투명 영상 품질을 검증한 것은 아닙니다.

1.7의 최신 별도 4K30·2초 자막 표본은 빈 화면 1.142초, 자막 1.626초였습니다. 같은 버전의 앞선 실행에서는 각각 2.035초·3.458초였습니다. 일반 Chromium 인수를 사용했고 다른 앱 부하와 캐시를 통제하지 않았으므로 성능 개선율이나 보장 수치로 해석하지 않습니다. 자막 합성은 CPU, 인코딩은 NVENC입니다.

## 1.7 투명 영상

투명 VP8·VP9 WebM과 스테레오 PCM 오디오를 포함한 VP9 MKV에서 FFmpeg 기본 디코더가 알파 평면을 버리는 문제를 재현했습니다. 해당 입력은 libvpx 디코더로 읽고, 투명 썸네일은 PNG로 만듭니다. 투명 프록시는 CPU로 VP9·Opus WebM을 생성하며 원본의 색상 정보를 BT709로 변환합니다. 일반 영상의 H.264 GPU 프록시 경로는 유지합니다.

- 세 원본의 실제 미리보기와 생성된 프록시에서 42개 프레임 선택이 원본 타임스탬프와 일치했습니다. 프록시의 처음 네 프레임 시각도 원본과 같았습니다.
- 실제 IPC의 CPU·NVENC 출력 여섯 건, 총 324프레임에서 원본 프레임 번호가 일치했습니다. 투명·반투명·불투명 영역을 파란 프로젝트 배경과 합성하고 실제 GPU 미리보기의 색과 비교했습니다. 손실 압축을 포함한 RGB 허용 차이는 채널당 8/255입니다. 별도 단위 검사에서는 불투명도 0.5도 검사했습니다.
- 원본과 프록시의 실제 스테레오 재생 피크·RMS가 기준 톤과 일치했습니다. 출력 MP4는 프로젝트 배경까지 합친 불투명 영상입니다.
- 새 캐시에서 예전 프로젝트를 열면 불투명 프록시를 제외하고 JPEG 썸네일을 PNG로 다시 생성합니다. 클립 ID·길이·편집 내용을 유지하는 실제 앱 검사도 포함합니다.

원본 Canvas2D 디코더와 GPU 합성의 비교에는 앞서 기록한 I420A 색상 근사 차이 때문에 채널당 4/255를 허용했습니다. 미리보기와 프록시의 색·알파를 각각 확인했으며, 모든 투명 코덱이나 HDR 품질을 검증한 결과는 아닙니다. 근거: `tests/media-alpha.test.ts`, `scripts/e2e-media-alpha.mjs`.

## 1.6 오디오 보정과 재생

클립별 6밴드 EQ와 프로그램의 스테레오 샘플 피크/RMS 미터를 추가했습니다. EQ는 주파수 20–20,000 Hz, 게인·출력 ±18 dB, Q 0.1–10 범위를 지원하며, 선반 기울기는 S=1입니다. 미리보기의 네이티브 IIR 필터와 출력 DSP는 같은 계수를 사용하고, 볼륨·페이드보다 먼저 적용합니다. AI 잡음 제거·LUFS·트루 피크 측정은 포함하지 않습니다.

- 실제 FFmpeg 및 WebAudio와 기준 PCM의 8조건 비교: 필터 종류 5개, 6밴드 조합, 바이패스, 평탄. 각 12,000 스테레오 프레임에서 최대 샘플 차이는 1.49×10⁻⁸입니다. 16비트 WAV와 기준의 차이는 최대 1/65,536로 양자화 범위 안입니다.
- 일반/곡선 속도에서 출력 블록 크기와 부분 출력 시작점을 바꿔도 EQ 상태와 샘플이 유지됩니다. 동일한 편집 구간을 두 번 분할한 144,000 스테레오 프레임도 분할 전과 바이트가 같습니다. 원본·효과·페이드·전환이 달라지는 경계는 별도로 처리합니다.
- 실제 EQ UI 13개, 미터 UI 12개, 연속 재생 UI 8개를 통과했습니다. 그래프 드래그의 단일 실행 취소, 숫자·키보드, 프리셋, 저장·복사, 다중 선택·잠금, 작은 창을 포함합니다. 미터의 병렬 분석을 켜고 껐을 때 9,600×2개 오디오 샘플이 정확히 같았습니다.
- 미터의 전송은 응답을 기다리는 메시지 하나로 제한합니다. UI가 220ms 멈춰도 오디오 스레드가 피크를 누적하고 처리 대기열이 계속 늘어나지 않았습니다. EQ는 빠른 변경 100회에서도 필터 체인 두 개와 마지막 대기 변경 하나로 제한했습니다.
- 첫 재생의 원본 오디오 시각이 프로그램 시계보다 약 0.23–0.32초 늦어져 보정 탐색을 유발하던 문제를 수정했습니다. 오디오 시각으로 진행하며, 500ms 재생 시작 지연을 주입해도 시작 부분을 건너뛰지 않았습니다. 분할된 영상·오디오를 실제 재생할 때 두 컷에서 디코더 교체·필터 초기화·탐색이 없고 음량은 -15.9382 dBFS로 유지됐습니다. 이는 해당 합성 톤 표본의 결과입니다.

명시적으로 다른 시각을 탐색하면 필터 상태를 다시 준비하며, 모든 탐색 위치에서 출력과 같은 사전 처리를 하는 기능은 아직 없습니다. 미리보기의 리미터는 유한 압축비를 사용해 과도한 입력에서 0 dBFS를 넘을 수 있습니다. 미터는 미리보기 음소거 전 값을 보여주며 최종 파일의 계측 결과가 아닙니다.

CPU DSP만 분리한 48 kHz·5초·32클립·각 6밴드 표본은 0.383/0.341/0.328초였습니다. 디코딩·음정 보존·믹싱·디스크·인코딩을 제외한 측정이며 전체 출력 성능 수치가 아닙니다. 포터블 압축은 같은 1.5 payload로 기존 압축 12.53/12.01초, ZIP 7.27/4.75초를 비교했고 추출 파일 전체가 같았습니다. 크기는 246→351MB로 증가합니다. 캐시와 외부 부하가 완전히 통제되지 않은 이 PC의 관찰이며 1.6 실제 EXE 검증을 대체하지 않습니다.

프로젝트 형식 6에 EQ를 저장하며 형식 1–5를 읽습니다. 1.0–1.5 앱은 형식 6을 열 수 없습니다. 근거: `tests/audio-eq.test.ts`, `tests/audio-continuity.test.ts`, `scripts/e2e-audio-meter.mjs`, `scripts/e2e-audio-eq.mjs`, `scripts/e2e-eq-continuity.mjs`.

## 1.5에서 추가한 색 보정과 스코프

전체·R/G/B 곡선, 3D .cube LUT와 강도·적용 전후 비교를 구현했습니다. LUT를 프로젝트에 포함하며 잠금·다중 선택·복사·실행 취소·저장 후 원본 LUT 이동을 실제 UI로 검사했습니다. 미리보기는 WebGL2, 출력의 색 보정은 FFmpeg CPU 필터이며 인코딩은 별도로 NVENC를 사용할 수 있습니다.

- 실제 FFmpeg 출력 8종의 최대 채널 오차 2/255. 33³·65³ LUT, 입력 도메인, 강도 0·우회, 알파 보존을 포함합니다.
- WebGL2·CPU 미리보기 16개 비교에서 최대 채널 오차 1/255. 실제 내보내기 창에서 만든 NVENC 영상 15프레임의 기준 대비 평균 YUV 차이는 0.3688/255였습니다. 표본 결과이며 모든 영상의 오차 상한을 뜻하지 않습니다.
- 색 보정 UI 13개와 스코프 UI 12개 통과. 스코프는 히스토그램·파형·RGB 퍼레이드·벡터스코프를 지원하며 최대 320×180, 초당 8회, 작업 하나로 제한합니다. 정지 중 색 변경·빠른 탐색·프로젝트 교체의 오래된 결과 폐기·소스 화면 전환·실제 GPU 컨텍스트 소실 후 CPU 전환을 검사했습니다.

스코프는 현재 합성 화면의 SDR 표본이며 전체 해상도/HDR 측정 도구가 아닙니다. HSL, Log/HDR 컬러 관리와 사용자 효과 체인은 미구현입니다. 프로젝트 형식 5는 LUT를 내장하며 이전 형식 1–4를 읽습니다. 이전 앱은 형식 5를 읽을 수 없습니다.

## 자막과 단어 시간

Whisper의 실제 단어 시간을 UTF-16 문자열 구간과 함께 보존합니다. 측정·수동·균등 추정 시간을 구분하며, 단어를 선택해 시작/끝 또는 현재 재생 위치로 수정할 수 있습니다. 글자를 바꾸면 기존 단어 연결을 지우고 실행 취소로 함께 복구합니다. 분할·트리밍·속도 커브의 시간 변환, 트랙 잠금, 스타일 일괄 적용, 저장 후 다시 열기를 포함한 실제 자막 UI 18개 검사를 통과했습니다.

새 자막은 번들 Noto Sans KR·Noto Color Emoji와 공통 Canvas 래스터를 사용합니다. 줄 배경·둥근 모서리·외곽선·그림자·자간·굵기·줄 높이·단어 강조·등장/퇴장 효과와 24개 사용자 스타일 저장을 지원합니다. 지원하지 않는 글자는 알리고 출력을 중단합니다. 임의의 사용자 폰트나 모든 문자·이모지 조합을 지원한다고 주장하지 않습니다. 기존 ASS 자막은 별도 경로를 유지합니다.

- 30·60·120fps와 세로/축소 출력의 원시 RGBA 70개 비교, 분할 중인 단어·애니메이션 시계, 기존 ASS와 새 자막의 겹침 순서, 출력 구간 경계와 취소 검사를 통과했습니다.
- 실제 120fps 출력 73프레임과 CPU 미리보기를 동일 BT.709 4:2:0 변환 후 비교하면 바이트가 같습니다. WebGL 미리보기의 최대 프레임 평균 오차는 0.0705/255, 자막 영역 밝기 평균 오차는 최대 0.6301/255입니다. 이 값은 해당 장면의 측정 결과입니다.
- Canvas/WebGL의 27개 스타일·정렬·강조 상태에서 최대 평균 RGB 차이는 0.01479/255였습니다. 자막 래스터 캐시 48MiB·32개, 레이아웃 96개·20만 문자, 출력 프레임 재사용 캐시 64MiB 제한을 검사했습니다.
- 작은 창에서도 자막 목록 높이 86px를 확보하고 단어 시간·현재 위치·스타일 저장 버튼의 실제 클릭 가능 여부를 검사했습니다. 프로젝트 120fps 표시와 기존 효과의 표시/변경/실행 취소도 포함합니다.
- 테스트의 로그 연결 종료로 발생했던 EPIPE 오류를 재현했습니다. 테스트 실행기는 로그 파일과 자식 프로세스를 소유하고, 로그 또는 부모 연결 종료 시 창 0개로 정리되는 것을 확인했습니다.

4K30·2초·60프레임의 합성 자막 표본에서 1.6에서 빈 화면 출력 1.587초, 자막 출력 2.466초였습니다. 이전 1.5의 2.850/5.662초와 부하·캐시 조건이 같다고 입증되지 않았으므로 코드 개선율로 해석하지 않습니다. 자막 합성과 일반 영상 합성은 CPU, 인코딩은 NVENC입니다. 13개 상태만 래스터화하고 47프레임을 재사용했습니다. 출력 캐시 측정 최대 3.75MiB, 프로세스 간 RGBA 전송량 48.80MiB입니다. 짧은 합성 표본이며 일반 영상 프로젝트의 속도를 뜻하지 않습니다.

저장/복구 파일은 50MiB, 단어 정보는 자막당 2,048개·프로젝트 전체 20만 개입니다. 같은 출력 구간에 섞인 새 자막/기존 ASS 그룹의 RGBA 프레임 합계가 256MiB를 넘으면 명확한 오류로 중단합니다. SRT에는 문구와 문장 시간만 저장됩니다.

## 1.3에서 추가한 전환과 원본 갱신

디졸브·와이프·밀어내기·줌, 네 방향(와이프·밀어내기), 진행 곡선과 선형·이퀄 파워·없음 오디오를 지원합니다. 클립 자체의 시작·길이·페이드·속도 커브를 바꾸지 않고 컷 앞뒤의 원본 여유 구간을 사용합니다. 전환 길이는 프로젝트 프레임 단위이며 출력 프레임률과 독립적입니다. 복사 후 프레임률을 바꿔 붙여넣어도 전환 시간을 가장 가까운 새 프레임으로 유지합니다.

실제 전환 UI 17개, 비동기 분석·취소 6개, 원본 교체·재연결 8개 검사를 통과했습니다. 잠금, 실행 취소, 두 클립 복제, 캔버스 선택·줌 드래그, 저장 후 다시 열기, 같은 프로젝트 ID를 다시 연 뒤 도착하는 오래된 결과를 포함합니다. 전환에 원본 여유가 부족하거나 다른 클립·전환이 겹치면 적용을 거부합니다.

원본·프로젝트 비동기 경계 7개 검사는 실행 취소가 교체 전 원본 정보·프록시를 되살리지 않는지, 오래된 프록시·자막·보정 결과가 현재 프로젝트에 들어오지 않는지, 지연된 열기·저장 완료가 새 프로젝트와 저장 경로를 덮어쓰지 않는지 확인했습니다. 처리 도중 실제 원본을 바꾸는 별도 검사에서 두 자막 엔진과 흔들림 보정 모두 결과를 게시하지 않았습니다.

- 실제 Electron WebGL2/Canvas2D에 현재 소스 렌더러를 넣어 180개 장면·360개 픽셀 비교를 수행했습니다. 불투명·반투명·변형 효과와 네 방향, 경계 시점을 포함하며 최대 장면별 평균 오차는 기준식 대비 0.385/255였습니다. 실제 앱의 번들 UI 검사는 위 흐름 검사에 별도로 포함됩니다.
- FFmpeg 전환 합성 14개 장면의 최대 채널 오차는 기준식 대비 1/255였습니다. 반투명 입력은 먼저 한 쌍으로 합성한 후 아래 트랙 위에 올리므로 디졸브 중 배경이 중복 비치지 않습니다.
- 네 전환 각각 96프레임에서 1초·6초 출력 구간의 영상 바이트가 일치했습니다. 전환 밖 71프레임과 전환 제거 후의 출력도 기존 결과와 같았습니다. 30fps 프로젝트의 24fps 출력, 프레임에 맞지 않는 컷, 페이드·마스크·변형 키프레임을 포함합니다. 실제 영상·속도 커브 입력도 90프레임의 구간별 바이트가 같았습니다.
- 세 오디오 모드의 최대 샘플 오차는 기준 게인 계산 대비 7.5e-09였습니다. 4096·777샘플 읽기 단위에서 PCM이 같고, 두 소스를 각 한 번씩 연속 디코딩했습니다. 원래 64개 제어점을 보존한 속도 커브의 앞뒤 0.5초 연장 검사에서 최대 시각 오차는 0.439ms였으며 취소 후 남은 프로세스는 0개였습니다.
- 10,000개 클립·9,999개 전환에서 여러 컷을 끊는 편집의 연결 갱신은 51.0ms였습니다. 전체 UI 반응 시간이 아닌 연결 갱신 함수 한 번의 측정입니다. 500개 무작위 원본·컷 조건을 별도의 프레임별 계산과 비교했습니다.

영상보다 오디오가 긴 파일, 지연 시작, VFR, 회전·편집 목록 등 실제 영상 범위 10개 샘플을 검사했습니다. 불명확한 원본은 필요할 때 프레임을 분석하고 취소할 수 있습니다. 원본 파일이 같은 경로에서 교체되면 이전 프록시·썸네일·디코더를 갱신합니다. 다시 열기에서 여유 구간이 사라진 전환은 해제하고 알리며 기존 프로젝트 파일은 그대로 둡니다. 내보내기는 연결된 원본이 바뀌었는지도 다시 확인합니다.

밀어내기·줌 출력은 실제 장치 검사를 통과하면 OpenCL GPU에서 16비트 평면·투명도와 FP64 좌표를 사용합니다. 나머지 클립 효과·일반 합성이 모두 GPU로 옮겨진 것은 아닙니다. 디졸브·와이프는 CPU의 최적화된 혼합 경로를 사용합니다. 출력의 **전환 처리 → CPU**는 GPU 인코더 선택과 독립적이며 GPU 전환이 실패하면 전체 출력을 새 스트림으로 CPU 재시도합니다.

GPU 전환 기준 픽셀 14개 장면과 밀어내기·줌 각각 96프레임의 1초·6초 구간 검사를 통과했습니다. 같은 GPU 경로의 구간 간 바이트는 같았고, CPU 대비 최대 차이는 2/255, 장면별 평균은 최대 0.000128/255였습니다. 전환 밖 프레임은 같았습니다. GPU 프레임이 이미 전달된 다음 고의로 실패시킨 검사에서 CPU 재시도 영상·오디오는 CPU 기준과 같고 중복 프레임이 없었습니다. 실행 중 취소 후 자식 프로세스와 게시된 출력은 0개였습니다. 다른 GPU·드라이버의 동일 성능은 검증하지 않았습니다.

아래 전환 성능 표는 1.3 소스에서 측정한 비교 기록이며, 현재 기능 회귀 검사와 구분합니다. 1920×1080·30fps·4초·120프레임, 컷의 1초 전환과 타원 마스크·크기·회전·불투명도를 적용한 두 이미지의 출력 시간입니다. 인코딩은 네 경우 모두 H.264 NVENC이며, 전환 이외 효과는 CPU에서 처리합니다. 출력 함수 호출부터 완료까지 측정했으며 입력 생성·초기 미디어 정보 분석·인코더 지원 검사는 제외합니다. 짧은 이미지 표본이므로 긴 영상 프로젝트나 다른 효과의 속도로 일반화하지 않습니다.

## 1.2에서 추가한 속도 커브와 흔들림 보정

영상·오디오의 속도 커브는 제어점 사이를 선형 보간하고 원본 시각은 속도를 적분해 계산합니다. 그래프 드래그·점 추가/삭제·위치와 속도 숫자 입력·5개 프리셋을 지원합니다. 속도 변경은 원본 시작·끝을 유지하며 타임라인 길이를 `원본 구간 ÷ 평균 속도`로 바꿉니다. 분할·트리밍은 남은 구간의 시각 연결을 유지하고, 이웃 클립·별도 자막은 자동 이동하지 않습니다. 광학 흐름 프레임 생성은 없습니다.

속도 UI 13개 검사는 그래프·숫자 입력·분할·트리밍·실제 디코더 탐색·저장 후 다시 열기와 MP4 출력을 포함합니다. 1초·6초 출력 구간에서 영상 489프레임의 해시가 일치했습니다. 오디오는 Rubber Band R3의 연속 위상 상태를 유지하고 분석 단계마다 원본 시각의 역함수를 적용합니다. 5개 일정/변화 속도 합성 음원에서 최대 시각 오차 9.262ms, 440Hz 음원의 측정 음정 440.00–440.00Hz였습니다. PCM 샘플 수·출력 구간 간 바이트 일치·MP4 영상/음성 싱크·분할·취소 정리도 검사했습니다.

60초·33개 제어점의 스테레오 합성 음원은 4.002초에 처리되었습니다. 네이티브 작업 집합 표본 최대 8.32MiB, JS PCM 버퍼 최대 156.9KiB였습니다. 기존 독립 처리 구간의 주기적 음량 저하를 없앴고 경계/일반 구간의 최소 RMS 비율은 0.9980였습니다. 이 값은 합성 음원 검사이며 일반 음악의 청감 품질 점수가 아닙니다. 영상보다 늦게 시작하거나 중간에 비는 오디오도 일정/커브 배속과 원본 트리밍 조합에서 위치·무음을 유지했습니다.

**남은 음질 제한:** 8초에 64개 제어점으로 0.1↔16배를 약 127ms마다 반복하는 극단적인 입력에서는 440Hz 음원의 일부 짧은 구간에 최대 +5.5Hz(21.5센트) 음정 흔들림이 측정되었습니다. 이 조건의 정확한 샘플 수·타이밍과 별개로 음정 보존은 완전하지 않으며, 일반 속도 검사 통과로 해당 제한을 숨기지 않습니다.

흔들림 보정은 CPU의 FFmpeg libvidstab 2패스로 선택 원본 구간을 처리합니다. 원본은 보존하고 사용자 데이터 폴더의 `media-derived`에 별도 H.264 CRF16 + PCM MOV를 저장합니다. 적용·해제 시 속도 커브와 효과를 유지하며 트리밍 후 해제도 원본의 해당 구간으로 돌아갑니다. 8비트 SDR 불투명 영상만 지원하고 HDR·고비트·투명 영상은 거부합니다. 자동 확대는 가장자리를 자르며 영상 재인코딩은 무손실이 아닙니다.

합성 흔들림 샘플의 위치 분산은 78.113 → 0.214806로 99.725% 감소했습니다. 82프레임과 PCM 131,088샘플을 유지했고 오디오는 바이트 단위로 일치했습니다. 동일 입력 20회에서 디코딩 RGB·분석 파일 해시가 모두 같았으며 Chromium에서 MOV 영상·음성 재생을 확인했습니다. VFR 44프레임, 최대 시각 오차 0.696ms, 지연 오디오·회전·비정사각 픽셀과 두 패스 취소 정리도 검사했습니다. 합성 이동 샘플의 결과로 실제 카메라 영상 전반의 품질 점수는 아닙니다.

이전 프로젝트를 현재 앱에서 저장하면 형식 5가 되므로 이전 앱에서도 사용할 파일이 필요하면 다른 이름으로 저장해야 합니다.

흔들림 보정 실제 UI 6개와 작업 완료·트랙 잠금 검사 8개를 통과했습니다. 원본 참조가 삭제된 클립의 붙여넣기, 잠긴 자막 수정, 잠긴 클립의 다중 페이드 적용을 차단하며 오래된 비동기 결과가 다른 프로젝트나 수정된 원본 구간을 덮어쓰지 않습니다. 영상 다운로드 UI·IPC·처리 코드와 새 배포 포함 목록에서 관련 기능을 제거했습니다.

## 저장과 파일 처리

- 프로젝트별 복구본, 겹쳐 실행한 저장의 순서, UTF-8 BOM 프로젝트 열기를 검사했습니다.
- Windows에서 대상 파일을 650ms 동안 독점 잠금한 상태에서도 원자적 저장이 재시도 후 완료되었습니다. 기존 파일을 먼저 삭제하지 않습니다.
- 폴더 연결(junction)로 경로가 달라져도 원본 미디어 덮어쓰기를 거부합니다.

## 제한과 미검증 범위

CapCut과 기능이 동등하지 않습니다. AI 배경 제거, 물체 추적, 광학 흐름, 멀티캠, 중첩 시퀀스, 협업, 템플릿 마켓은 없습니다.

출력의 동시 영상·이미지 입력과 오디오 입력은 각각 최대 32개이며 텍스트는 별도로 처리합니다. 미리보기는 활성 미디어 입력 합계 최대 32개입니다. 클립 10,000개는 계획기/UI 검사이고 장시간 출력 비교 기록은 50개 클립·66.562초입니다. 8비트 SDR을 대상으로 하며 HDR 톤 매핑은 없고, ASS의 1/100초 시간 단위와 Canvas 글자 렌더링 때문에 자막 표현에도 차이가 있습니다. 출력 구간 사이에는 `atempo` 상태를 유지하지만, 배속 클립을 별도 클립으로 분할했을 때 독립 `atempo` 인스턴스의 위상·과도음까지 같다고 보장하지 않습니다.

다른 PC, 수 시간 분량의 복잡한 출력, 실제 설치형 프로그램 설치 절차는 검증하지 않았습니다. 포터블과 설치형은 Windows 코드 서명이 없습니다.
